## 2. What is packaged today

### 2.1 Artefacts

| Artefact | Built by | Notes |
|---|---|---|
| `nexus-fabric-<ver>-windows-x64-setup.exe` | `packaging/windows/build.sh` + `installer.nsi` | NSIS, per-user |
| `nexus-fabric-<ver>-windows-x64-portable.zip` | same | `zip`, or PowerShell `Compress-Archive` on a Windows host |
| `nexus-fabric-<ver>-linux-x86_64.tar.gz` | `packaging/linux/build.sh` | launcher `nexus-fabric.sh`, `.desktop` template |
| `SHA256SUMS` | `packaging/build_all.sh` | check with `cd dist && sha256sum -c SHA256SUMS` |
| `README.txt`, `NOTICE.txt`, `THIRD_PARTY_NOTICES.txt` | shipped in every package | notices generated by `packaging/generate_notices.sh` (cargo-about) |
| `packaging/INSTALL.md` | English + Japanese install guide | end-user instructions |

One binary, two names: `nexus-fabric.exe` (Windows) and `nexus-fabric` (Linux). Version comes from `[workspace.package] version` in `Cargo.toml`. Windows exe is cross-built with `x86_64-pc-windows-gnu` + mingw-w64; `rusqlite` bundles SQLite, so no SQLite DLL is needed. macOS is not packaged.

### 2.2 Installer behaviour (verified under wine only)

| Behaviour | State |
|---|---|
| Install path `%LOCALAPPDATA%\Programs\NexusFabric`, `RequestExecutionLevel user` | no administrator rights needed |
| Start-menu shortcut (required), desktop shortcut (optional, ticked) | present |
| Development-build notice on the welcome page | present |
| Uninstaller registered under the current user | present |
| Uninstall keeps the data folder unless "Also delete my data" is ticked | keeps data; **the deletion path was not exercised** (silent mode skips that page) |
| Uninstall refuses while `nexus-fabric.exe` is running | present |

### 2.3 Runtime facts that matter to factory IT

| Fact | Detail |
|---|---|
| Desktop mode | `nf-server --desktop`; loopback only, `127.0.0.1:8787` (`--port N` preferred, free loopback port if busy); allowed host names `127.0.0.1`, `localhost` |
| Data folder | Windows `%LOCALAPPDATA%\NexusFabric\data`; Unix `$XDG_DATA_HOME/nexus-fabric` or `~/.local/share/nexus-fabric`, created 0700. Windows inherits the profile ACL; **no explicit ACL is set** |
| Network | no outgoing calls, no telemetry, no updater; offline first launch tested on Linux in a loopback-only network namespace (`unshare -n`) |
| Single instance | exclusive lock on `desktop.lock`; second copy on the same data folder refused |
| Browser | opens default browser (`explorer.exe` / `xdg-open`); `--no-browser` prints the address |
| First-run token | 32 random bytes, hex, delivered in the URL fragment `#setup=<64 hex>`; never sent to the server; only its SHA-256 stored; forgotten after the first administrator exists |
| Shutdown | Ctrl+C, Ctrl+Break, console close (Windows); SIGTERM/SIGINT/SIGHUP (Unix); SQLite WAL checkpointed before exit |

### 2.4 The PDF converter — not in the package, and blocked

- `competitors_japan.md` §4 records "PDF → DXF inside the product … **DONE 3.1 (converter not yet in downloadable packages)**", with Japanese PDF handling planned as 5J.3.
- `MASTER_GOAL.md` capability matrix says drawing/DXF import is **not implemented**, documents are stored encrypted and **never parsed**, and no parser may be merged without an isolated, network-less, resource-limited process and fuzz tests. `RELEASE_READINESS.md` lists V-26 "no parser sandbox" as a blocking condition for any parser. DXF import needs an owner decision.
- **Conclusion for packaging:** ship the converter *beside* the program only after (a) the two status documents are reconciled on one commit, (b) the sandbox condition is met, (c) the founder approves the scope. Until then the download page must not advertise PDF input. **To verify:** actual state of task 3.1 on the release commit — read `docs/IMPLEMENTATION_STATUS.md`, `docs/project/CLI_WORK_PLAN.md` 3.1/5J.3 and the converter's own tests.

## 4. Target distribution design

### 4.1 Download site

| Element | Design | Basis / gap |
|---|---|---|
| Channel | own site, direct download of installer + portable zip + Linux tar.gz | CADTOOL sells packaged media only, "no download sale yet" (`competitors_japan.md` §1.1) — a real differentiator |
| Integrity | publish `SHA256SUMS` next to every file; instructions in EN/JA | already produced by `build_all.sh`; `PACKAGING.md` tells users to check them |
| Authenticity | **signatures over `SHA256SUMS`**, published key fingerprint on a second channel | does not exist today — **to verify**: choose and document a signing method; no signature tooling is in the repository |
| Evidence pack | publish `MANIFEST-<commit>.md` per release, including its fixed "What this does NOT show" section | produced by `verify_release.sh` |
| Wording | development build, not validated, not for manufacturing, not for confidential data, on the page, in the installer and in first run | `README.md`, `LEGAL_READINESS.md` §1 item 1, §2 item 3 |
| Price page | none until the founder decides; competitor anchors in §9 | `competitors_japan.md` §4 D7 "NOT PLANNED (owner decision)" |
| Hosting, domain, TLS, download logs | **to verify** — operator obligations for a hosted server are listed as open lawyer questions | `LEGAL_READINESS.md` §4 q6; `PRIVACY_STATEMENT.md` placeholders |

### 4.2 Windows code signing

| Item | Position |
|---|---|
| Today | unsigned; SmartScreen warning expected (`PACKAGING.md`) |
| OV certificate | option: organisation-validated. Cost, issuance time, identity documents required for an Indian entity, token/HSM handling: **to verify** with a certificate authority reseller; nothing in the context states any price |
| EV certificate | option: extended validation. Cost, hardware/cloud-token requirement, and whether it changes SmartScreen behaviour immediately: **to verify** with the CA and Microsoft's current SmartScreen documentation |
| SmartScreen reputation | how reputation accrues for OV vs EV, and what a factory sees when SmartScreen is enforced by group policy: **to verify** on a real Windows 10/11 PC (M1) |
| Scope | sign `nexus-fabric.exe` **and** the installer; timestamp the signature so it outlives the certificate (provider/method: **to verify**) |
| Where | `packaging/windows/build.sh` and the `windows-latest` job of `release.yml`; build scripts sign nothing today |
| Decision | buying a certificate is a FOUNDER DECISION (§9) |

### 4.3 Offline installer and licence delivery

- The installer already needs no admin rights and the program makes no outbound calls — this is the strongest fit for 工場 PCs that are offline or air-gapped. Competitors point the other way: Cutwise Unfold needs a Microsoft account and a Store licence check, Design2Fab needs internet for its licence (`competitors_japan.md` §1.3, §1.21).
- Deliver the licence as a **file shipped in the package** (`LICENSE`/terms text) plus a first-run acceptance screen. Neither exists: packages carry the "evaluation use only" sentence and there is no acceptance screen (`LEGAL_READINESS.md` §4 q9).
- **No licence key, no dongle, no phone-home** is the recommended design; any enforcement mechanism is new work and must not break offline use. Licence model, evaluation length and fees are FOUNDER DECISIONS.
- Japanese legal text is required for Japan; all three drafts need a native-speaking lawyer admitted in Japan (`LEGAL_READINESS.md` §4).

### 4.4 Update channel, rollback, backup, uninstall

| Topic | Design | Current basis |
|---|---|---|
| Update check | manual only: user opens the download page and compares version + checksum | "No automatic update exists, by design; nothing checks for new versions" (`PACKAGING.md`) |
| Signed update manifest | optional P1: a signed JSON listing version, file names, SHA-256, signature; the program may *display* it, never install | new work; must not add outbound calls in desktop mode without an explicit opt-in and a documented change to the offline claim |
| Silent auto-update | **never** in a factory; a part program must not change under an operator | consistent with the no-updater design |
| Rollback | keep the previous `setup.exe`; `verify_release.sh --previous <older setup.exe>` already exercises an upgrade check under wine | `PACKAGING.md`; run the same on a real PC |
| Database compatibility across versions | **to verify** — no migration/rollback statement exists in the context; check `crates/nf-server/src/storage.rs` and the upgrade path before promising rollback |
| Backup before update | documented cold copy: stop the program (graceful stop checkpoints the WAL), copy the whole data folder, then install | `PACKAGING.md` shutdown behaviour; no product backup tooling (M8) |
| Restore test | restore the copied folder on a second machine/profile and start | `READINESS.md` production target requires "tests against a copied data folder" |
| Uninstall | keeps data unless the user ticks "Also delete my data"; refuses while running | implemented; the deletion path is untested (M1) |
| Hosted server | `deploy/nf-backup.sh` keeps 14 backups; a daily backup with restore test runs on the owner's server | `LEGAL_READINESS.md` §4, `MASTER_GOAL.md` |

## 5. Factory IT realities in Japan (製缶 / 板金 shops)

| Reality | How we handle it | Evidence / gap |
|---|---|---|
| Offline / air-gapped PC (オフライン) | full offline installer; no telemetry, no updater, no licence call; loopback-only server; offline launch already tested on Linux with `unshare -n` | `PACKAGING.md`; **repeat the offline test on a real Windows PC** |
| No administrator rights (管理者権限) | per-user install to `%LOCALAPPDATA%`, `RequestExecutionLevel user`; portable zip as fallback | `PACKAGING.md`; whether a factory policy blocks per-user installers: **to verify** on site |
| Application allow-listing / software approval (稟議・申請) | publish version, SHA-256, signature, third-party notices, and the release manifest as an evidence pack for the IT department | notices file + manifest exist; approval process at each customer: **to verify** with the factory |
| Antivirus false positives (ウイルス対策) | signing, per-user install, no outbound traffic, published hashes; submit the signed binary to the customer's AV vendor if flagged | no AV testing is recorded anywhere in the context — **to verify**: which AV products the target factories run, and each vendor's false-positive submission process |
| Proxy servers (プロキシ) | desktop mode needs no proxy at all; for the hosted server, TLS must come from a proxy (V-20: no TLS in the server) and client addresses are taken from the peer or a trusted proxy | `RELEASE_READINESS.md`, `LEGAL_READINESS.md` §4 (`deploy/Caddyfile`, `main.rs:3252-3261`) |
| Download blocked on the shop PC | deliver via IT-approved transfer or physical media; the portable zip runs without installation | competitor precedent: CADTOOL is CD-ROM media, Japanese-language OS required (`competitors_japan.md` §1.1) |
| Japanese-language OS, legacy Windows | our Windows build is x64 and unverified on a real PC; supported Windows versions are **not stated** in `PACKAGING.md` — **to verify** and publish a tested list | `PACKAGING.md`, `READINESS.md` D6 |
| Browser policy / default browser blocked | `--no-browser` prints the address; allowed hosts are `127.0.0.1` and `localhost` | `PACKAGING.md`; `explorer.exe` opening is untested on Windows |
| Data folder copied off the PC | inside the threat model; restricted-deployment class requires OS disk encryption, individual OS accounts, documented backup/recovery, and an honest statement that the database is not encrypted | `READINESS.md` desktop classes; `docs/security/DESKTOP_KEY_ASSESSMENT.md` |
| Shops that draft in Jw_cad | JWW output is design-only (5J.6); do not advertise it | `competitors_japan.md` §1.8, §4 |
