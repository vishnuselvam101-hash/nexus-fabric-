# PDF to DXF converter (`crates/nf-pdf`, binary `nf-pdf2dxf`)

Status: work plan task 3.1. A deterministic, offline converter from one vector PDF page to DXF R12 (AC1009), as a library and a command-line program, started by the server for a PDF document of a project (section **In the product**), with an interface screen in English and Japanese. Review C findings RC-05, RC-06 and RC-06-N1 are addressed here. Outputs are marked NOT RELEASED and labelled "Converted from PDF - not verified - not released".

## What is converted

- Stroke paths `S s B B* b b*` go to `PDF_STROKE`. Closed subpaths (`h`, `s`, `re`) are closed polylines.
- Dashed strokes (non-empty `d`) go to `PDF_DASHED` as the on-pieces of the pattern. Dash lengths scale by the square root of |det| of the CTM at paint time (exact for uniform scaling).
- Filled-only paths `f F f*` go to `PDF_FILL` as outlines. `B` and `b` produce both. `--no-fill` removes `PDF_FILL` output.
- Curves are flattened in output millimetres. For a cubic with `M = max(|P0-2P1+P2|, |P1-2P2+P3|)` the piece count is `n = ceil(sqrt(3M / (4 tol)))`, and the chord error is at most `3M / (4 n^2) <= tol`. Measured against 4001 exact samples per test curve: 0.00707 mm at tol 0.01, 0.03395 mm at tol 0.05, 0.33333 mm at tol 0.5.
- `q Q cm` with the full matrix; Form XObjects (depth limit 16); `/Rotate` 0, 90, 180, 270; MediaBox and CropBox origin (visible box = CropBox clipped to MediaBox); `/UserUnit`.
- Text (`Tj TJ ' "`) becomes `TEXT` on `PDF_TEXT` only where the decoding is reliable: WinAnsi; the ASCII ranges of StandardEncoding and MacRomanEncoding; `/Differences` with ASCII or `uniXXXX` names; ToUnicode CMaps (`bfchar`, `bfrange`) for simple and Identity-H fonts. Anything else is skipped and counted with a reason. Characters outside printable ASCII (and `%`, `^`) are written as `?`.
- Dimension text is never read as geometry or as a scale.

## Scale rule

- One PDF user-space unit is 1/72 inch of paper, multiplied by `/UserUnit` when present.
- One PDF point on paper is 25.4/72 mm. A drawing scale 1:N therefore gives `mm per point = 25.4/72 * N` (1:10 gives 3.527777...).
- Output millimetres per user unit = mm per point * UserUnit.
- Give either `--mm-per-point X` or `--scale 1:N`. With neither, the converter refuses (`scale_required`). It never guesses.

## Accuracy statement

The DXF reproduces what is drawn in the PDF, at the scale supplied. A drawing is not necessarily to scale. Dimension text is not interpreted. The result is not a flat pattern, has not been checked against any manufacturing requirement, and carries the NOT RELEASED marking on layer `NF_NOT_RELEASED`.

## Output

- DXF R12 (AC1009), layers `PDF_STROKE` (7), `PDF_DASHED` (3), `PDF_FILL` (5), `PDF_TEXT` (2), `NF_NOT_RELEASED` (1). Origin at the lower-left of the visible page, upright.
- Leading 999 comment lines: `NF-SOURCE`, `NF-SOURCE-SHA256`, `NF-PAGE`, `NF-SCALE-MM-PER-POINT`, `NF-UNITS: mm`, `NF-CHORD-TOLERANCE-MM`, `NF-CONVERTER-VERSION`, `NF-USER-UNIT`, `NF-PATHS-PAINTED`, `NF-SEGMENTS`, `NF-TEXT-SKIPPED`.
- Two TEXT notes above the page on `NF_NOT_RELEASED`: `CONVERTED FROM PDF - NOT VERIFIED - NOT RELEASED` and the scale used.
- JSON report (`--report`): status, refusal, source hash, page and page count, scale, user unit, rotation, boxes, tolerance, counts, bounding box (mm), warnings with counts, text skipped by reason, output hash, and the accuracy notes.

## Refusals (exit 2), limits (exit 3), internal errors (exit 70)

Refusals carry a code and a message on stderr as JSON, and no DXF is written:
`encrypted`, `malformed`, `unsupported_filter`, `page_out_of_range`, `raster_page` (a page-covering image and at most 10 painted paths: scanned drawings cannot be converted reliably and are not supported), `no_vector_paths`, `scale_required`, `scale_ambiguous`, `invalid_scale`, `invalid_tolerance`, `invalid_page`, `invalid_arguments`, `input_unreadable`, `output_unwritable`.

Internal errors (exit 70, `status: internal_error`): `isolation_failed` (the worker could not isolate itself; it converts nothing), `worker_start_failed`, `worker_failed` (the worker ended without an answer, for example by a signal; the message names the signal), `internal_error` (a panic caught in the worker), `output_write_failed`, `report_write_failed`. A DXF exists under the output's name only after exit 0 (RC-06-N1): a file of that name from an earlier run is removed at the start, the DXF is written to `<out>.partial` and renamed only after the full report has been written, and the report holds `status: incomplete` from the start until the answer replaces it (written to `<report>.partial`, then renamed). A program ended from outside (a signal, the caller's own kill) therefore leaves no file under the output's name and a report that says `incomplete`, never an empty file; its worker ends with it (PR_SET_PDEATHSIG). Test: `a_program_killed_from_outside_leaves_no_dxf_and_an_incomplete_report` (SIGKILL while the worker waits for input on a FIFO; checks the output, the report and that the worker is gone).

### Limits of the conversion

Exceeding one gives exit 3, `code: limit_exceeded`, and `limit` names it. **Every value below is an implementation limit of this converter** (a bound on memory and time chosen for this program), not an engineering value and not a value from a standard. Defaults are in `Limits` (`src/limits.rs`).

| `limit` | value | where it is enforced | tests |
|---|---|---|---|

Initial buffers are never larger than the budget left | `limit_decoded_bytes_total_budget`; `limit_decoded_bytes_is_checked_inside_ascii85`; `limit_decoded_bytes_is_checked_inside_ascii_hex`; `ascii85_after_flate_and_runlength_stops_at_the_budget_with_default_limits`; unit `ascii85_and_ascii_hex_stop_at_the_budget_inside_the_loop` |

| `graphics_depth` | 256 nested `q` | `interp.rs` | `limit_graphics_nesting` |

## Isolation

The program runs as two processes. The **parent** checks the arguments, opens the input, creates the output and report files, and starts a copy of itself as the **worker**: no environment (on Windows only `SystemRoot` is kept), the input file as its standard input, a pipe as its standard output. The worker isolates itself **before it reads any input**, converts, and sends its answer (exit code, message, report, DXF) through the pipe. The parent never parses PDF data; it checks the answer, writes the report and the DXF, removes the output after any failure (including a worker that crashed, was stopped by a limit or ran past 90 s), and exits. The report's `isolation` entry says what was applied to the worker.

**Linux** (the worker, in this order, in `src/bin/nf-pdf2dxf/sandbox.rs`):
1. It is ended with SIGKILL if the parent ends (PR_SET_PDEATHSIG); if the parent has already ended it stops.
2. Resource limits (setrlimit, through rustix): the table above.
3. Landlock: every file-system access right, TCP bind and connect (UDP from Landlock ABI 10), abstract UNIX sockets and signals to other processes are handled, and no rule grants any of them. The worker cannot open, create, remove, execute or list anything by name, its own input and output included. On a kernel that supports only an older Landlock ABI the rights of later ABIs are not enforced and the report says so (this host, Linux 7.0: ABI 8, so ResolveUnix (ABI 9) and the UDP rules (ABI 10) are not available). On a kernel without Landlock (before 5.13, or not enabled at boot) the worker continues without this layer and the report says `not enforced`; step 4 still refuses every file-system and socket call.
4. A seccomp allow-list (seccompiler): `read`, `readv`, `write`, `writev`, `close`, `munmap`, `mremap`, `madvise`, `brk`, `futex`, `getrandom`, `clock_gettime`, `sched_yield`, `rt_sigreturn`, `rt_sigprocmask`, `rt_sigaction`, `sigaltstack`, `restart_syscall`, `getpid`, `gettid`, `exit`, `exit_group`; `mmap` and `mprotect` only without PROT_EXEC; `tgkill` only to itself. Every other call fails with EPERM: no `socket` or `socketpair` of any family, no `open`/`openat`, no `execve`, no `clone`/`fork`, no `ptrace`, no `io_uring`. A call through another architecture's ABI ends the process. A system trace of real conversions shows only `read`, `write`, `mmap`, `munmap`, `getrandom`, `rt_sigprocmask`, `sigaltstack` and `exit_group` after the filter.

Steps 1, 2 and 4 are required: if one fails (for example a kernel without seccomp filters, or an architecture other than x86_64, aarch64 or riscv64) the worker converts nothing and the program exits 70 with `isolation_failed`. No namespace is used, so the isolation works for an unprivileged child of a service with `RestrictNamespaces=true`.

**Not isolated on Linux:** the parent process (it handles file names and bytes it does not parse); the system calls on the allow-list themselves (kernel attack surface); CPU and memory up to the limits above.

**The service unit** (`deploy/nf-server.service`). The earlier version of this section said that under `SystemCallFilter=@system-service` every conversion fails with SIGSYS. Measured on this host (systemd 259.9, transient units with the unit's filter, `NoNewPrivileges`, `RestrictNamespaces=true`, `MemoryDenyWriteExecute=true`, `ProtectSystem=strict`): the conversion **succeeds** under `@system-service` alone, with Landlock and the seccomp allow-list both reported as applied; with `SystemCallFilter=~landlock_create_ruleset` it fails closed (exit 70, `worker_failed`, signal 31, SIGSYS, no DXF). `systemd-analyze syscall-filter @system-service` does not list the Landlock calls, so why they are allowed was not established. The unit now allows `SystemCallFilter=@sandbox` explicitly, so the conversion does not depend on what a systemd version puts into `@system-service`; under any filter that refuses them a conversion fails closed and nothing is stored. The unit's `MemoryMax=1G` is lower than the worker's 2 GiB address-space limit: under the unit the cgroup limit binds first, and a conversion that needs more memory ends with the worker killed (exit 70, `worker_failed`, signal named) and nothing stored; the server runs one conversion at a time. `RestrictNamespaces=true` means `unshare -n` is not available to the server; no network namespace is used (see below).

**Windows:** the worker puts itself in a Job Object: process memory 2 GiB, user CPU time 60 s, one active process (it cannot start a child process), and it ends on an unhandled exception instead of showing a dialogue. **There is no network isolation and no file-system isolation on Windows**: the worker can open sockets and files with the rights of the user running it. The Job Object calls are `unsafe` (the Windows API is only reachable through `extern` functions, and the available safe wrapper, win32job 2.1.0, cannot set these three limits), so they are in a separate crate, `crates/nf-pdf/winjob` (`nf-pdf-winjob`, three `unsafe` calls with their reasons); `nf-pdf` and the program keep `#![forbid(unsafe_code)]`. This code was compile-checked and linted (`cargo clippy -p nf-pdf --all-targets --target x86_64-pc-windows-msvc -- -D warnings`, clean) on this Linux host; it has **not been run** (no Windows machine here). The server's Windows build was not compiled here (its SQLite C code needs a Windows C compiler); the release workflow compiles and tests both on `windows-latest` (`cargo test --workspace`, and `cargo build --release -p nf-pdf --bin nf-pdf2dxf`).

**Other Unix systems:** resource limits only; no network or file-system isolation.

**Tests** (`tests/isolation.rs`, Linux): the program is run with `--isolation-probe`, and after each step the worker itself attempts what the step must stop and writes one line per attempt on stderr, then converts as usual. `the_worker_has_its_resource_limits_before_reading_input` (the five limits); `landlock_refuses_every_file_tcp_and_program_access` (after step 3: reading /etc/hostname and its own input by name, writing its output by name, creating a file beside the output, a TCP connection to 127.0.0.1:9, running /bin/true: all EACCES); `seccomp_refuses_sockets_files_and_new_programs` (after step 4: TCP, UDP over IPv6, UNIX sockets, a socket pair, the file attempts and running /bin/true: all EPERM); `an_isolated_worker_still_converts_and_the_report_says_how_it_was_isolated`. Each was shown to fail with its step removed (and the other three to pass): without the resource limits the limits test fails; without Landlock the Landlock test fails; without seccomp the UDP, UNIX socket and socket pair attempts succeed and the seccomp test fails. The Landlock test needs a kernel with Landlock (5.13 or later, enabled) and TCP rules (6.7 or later); it fails, with that reason, on a kernel without them.

## In the product (server and interface)

**Server** (`crates/nf-server/src/pdfconv.rs`). The server never parses PDF data. `POST /api/documents/{id}/pdf-to-dxf` (roles admin and engineer, members of the document's project; a viewer gets 403, a non-member 404) with `{page, scale_kind: "ratio" | "mm_per_point", scale_value, tolerance_mm?, include_fill?, include_text?}`:

1. The request is checked first, with the converter's own codes where the rule is the same: no scale → `scale_required` (nothing is guessed); a scale kind other than the two, or a value that is not a number → `invalid_scale`; a page that is not a whole number from 1 to 100,000 → `invalid_page`; a tolerance that is not a number → `invalid_tolerance`; a flag that is not true/false → `invalid_arguments`; a document not detected as PDF → `not_a_pdf`. These answers (422) record nothing.
2. The stored PDF is decrypted and verified (hash) and written, owner-only, into a fresh owner-only directory `<data>/convert-tmp/c-<random>`. The program `nf-pdf2dxf` (the file beside the server executable, or `NF_PDF2DXF`) is started there: **no inherited environment** (on Windows only `SystemRoot`), standard input closed, standard output discarded, standard error read up to 256 KiB. The server stops it after **110 s** (its own timeout, longer than the program's 90 s worker limit and shorter than the default 120 s request limit); the waiting is done by a blocking task that holds the one conversion slot, so the timeout and the slot hold even when the request itself is dropped. The working directory is removed after every conversion and at start-up.
3. Outcome. Exit 0: the DXF is accepted only if the report says `status: converted`, the report's `output.dxf_sha256` equals the SHA-256 of the DXF file, and the report's `isolation` entry confirms the isolation of the platform (Linux: the seccomp allow-list and the resource limits; Windows: the Job Object; other Unix: the resource limits). Otherwise the answer is 503, nothing is stored. Exit 2 or 3: the converter's `status`, `code`, `limit` and `message` are passed to the client unchanged (422). Exit 70, a signal, a start failure or the server's timeout: 503 with `infrastructure: true`, an audit entry `pdf_conversion_unavailable`, nothing stored.
4. Records. A converted or refused conversion is stored as an append-only row of `pdf_conversions` and a record of kind `pdf_conversion` (family Activity) with a `derived_from` relation to the PDF's source record; its payload holds the source hash, page, scale, tolerance, options, converter version, status, code, limit, message, the DXF and report hashes, the label and `release_state: NOT RELEASED`. A successful conversion adds two documents to the project, the DXF (`NOT-RELEASED_from-pdf_<name>.p<page>.dxf`) and the JSON report (type `pdf_conversion_report`), encrypted like every document, each pointing to its conversion (`documents.conversion_id`), and a new project snapshot. Audit entries: `pdf_converted`, `pdf_conversion_refused`, `pdf_conversion_unavailable`, `pdf_conversion_download`. No row is updated; no new database table is read by the calculation code.
5. Reading: `GET /api/pdf-conversions/{id}` (the conversion and its report), `GET /api/pdf-conversions/{id}/dxf` and `/report` (downloads named `NOT-RELEASED_from-pdf_conversion<id>_p<page>_<hash>.dxf|.report.json`); any role that can read the project. The project answer lists its conversions.

A conversion is **never a flat pattern and never attached to a calculation**: calculations take their geometry from the request only (no endpoint takes a document as input), a conversion creates no calculation, and every answer carries `label: "Converted from PDF - not verified - not released"`, `release_state: "NOT RELEASED"`, `flat_pattern: false`.

**Limits through the server.** The upload limit (50 MiB, `membrane::MAX_UPLOAD_BYTES`) is lower than the converter's input limit (64 MiB), so `input_bytes` cannot be reached through the server. Reached and tested through the API: `compression_ratio`, `nesting`, `operands`, `graphics_depth`, `collection_items`, `total_items`, `operators`, `form_depth`. Not reached through the API (tested on the converter itself, table above; they pass through the same code path, exit 3, `code: limit_exceeded`, `limit` named): `objects`, `xref_sections`, `path_segments`, `text_items`, `decoded_bytes`, `output_bytes`, `wall_clock`.

**Isolation as the server applies it.** The isolation is the converter's own (section Isolation), confirmed by the server from the report before a DXF is accepted. The service unit has `RestrictNamespaces=true`, so `unshare -n` (a network namespace) is not used: on Linux the worker has no socket at all (seccomp) and Landlock refuses TCP. **Not isolated on Windows:** network and file system — the worker can open sockets and any file the service account can open; only memory (2 GiB), user CPU time (60 s) and child processes (none) are limited by the Job Object. Windows also has no parent-death signal: if the program's parent is killed, the worker runs on until its Job Object limits or its input end it. None of the Windows behaviour has been run (no Windows machine here). **Not isolated on Linux:** the program's parent process (it handles file names and bytes it does not parse) and the server itself (it decrypts the PDF into the working directory for the time of the conversion).

**Interface** (`web/app.js`, English and Japanese in `web/i18n.js`). On a project's source documents, a PDF row has a "Convert to DXF" action (not for viewers). The form asks for the page, how the scale is given (drawing scale 1:N, or millimetres per PDF point), the scale value (required: the form refuses to send without it), an optional chord tolerance (blank: the converter's default) and whether to include filled outlines and text. A refusal is shown with the converter's code and message and a link to the recorded refusal. The result page states "Converted from PDF - not verified - not released" and that the drawing is not a flat pattern; it shows the report (status, page and page count, scale, tolerance, bounding box, counts, warnings, text skipped by reason, converter version, source hash), a still line drawing of the DXF's polylines (not the pattern viewer; text is not drawn), and the downloads. Converted documents carry the label in the document list, and a project lists its conversions.

**Server tests** (`crates/nf-server/src/tests/pdfconv.rs`, with the real converter `target/<profile>/nf-pdf2dxf`, built by `cargo test --workspace`; without it the tests fail, they are never skipped): success, storage, record, audit and downloads; every refusal code (server and converter) with nothing stored; eight limits by name; roles; the converter started by the server, run with `--isolation-probe` through a wrapper: TCP, UDP, UNIX sockets, socket pairs, files by name and new programs refused, limits set; a converter that runs too long is killed (process gone) with nothing stored, and it saw no inherited environment; a DXF with a wrong hash or a report without the isolation is not accepted; a missing converter and a busy slot; a stale working directory removed at start-up; a fuzz corpus through the server path. Browser (`tests/ui_smoke.js`, both languages): the action, the form refusing without a scale, a converter refusal with its code, the label, the preview (not the pattern viewer), the DXF download with the NOT RELEASED note, no calculation from a conversion, and the Japanese screens without stray English.

## Fuzzing

- `tests/fuzz.rs`: seeded and deterministic. Mutations of valid files (bit flips, byte edits, token insertion, deletion, duplication, truncation, splices), random operator streams with huge and NaN-like numbers, and deep nesting.
- `tests/proptest_fuzz.rs` (proptest 1.12.0): four properties over generated input, each checking the contract that holds for any input (no panic; returns within its own time limit; a refusal or limit has a code and a message and no DXF; a success is a DXF that nf-dxf reads and that carries the NOT RELEASED note): any bytes with and without a PDF header; a valid page around generated content streams (plain or Flate); generated filter chains (ASCIIHex, ASCII85, RunLength, Flate, two-stage chains, unsupported filters) with generated predictor parameters and damaged data; generated nested objects in the page and resource dictionaries. `PROPTEST_CASES` sets the count (256 per property by default).
- Server path (`crates/nf-server/src/tests/pdfconv.rs`, `mutated_pdfs_through_the_server_end_in_a_conversion_or_a_refusal`): mutated PDFs are uploaded and converted through the API with the real converter; every answer must be 200 (converted) or 422 (refused, with a code, and no DXF document stored). `NF_PDF_SERVER_FUZZ_CASES` sets the count (150 by default).
- Bounded campaign run for task 3.1 (2026-11-21, release build, inside the development sandbox): `tests/fuzz.rs` 200,000 cases: 23,184 converted, 162,390 refused, 14,426 limit exceeded, 0 panics, 0 over the 1,000 ms bound, slowest 137 ms (43 s). `tests/proptest_fuzz.rs` with `PROPTEST_CASES=25000`: 4 properties x 25,000 cases, 0 failures (36 s). Server path, 1,500 cases: 186 converted, 1,314 refused, 0 other answers (68 s). No finding.
- A regression test covers the tiny-dash-pattern case found during development.
- cargo-fuzz is not installed in this environment (and needs a nightly toolchain), so no `cargo fuzz` target was added; proptest is used instead.

## Dependencies and licences

Fetched from crates.io and pinned in `Cargo.lock`. No network code, no OCR, no AI. The PDF parser is our own; no PDF crate is used.

- flate2 1.1.11, MIT OR Apache-2.0, with the pure-Rust backend miniz_oxide 0.9.1 (MIT OR Zlib OR Apache-2.0), adler2 (0BSD OR MIT OR Apache-2.0), crc32fast (MIT OR Apache-2.0), simd-adler32 (MIT).
- sha2 0.10.9, MIT OR Apache-2.0, with digest, block-buffer, crypto-common, cpufeatures, cfg-if, generic-array (MIT), typenum (MIT OR Apache-2.0).
- rustix 1.1.6, Unix only, Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT, with bitflags (MIT OR Apache-2.0) and linux-raw-sys (Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT).
- Linux only, for the worker's isolation: landlock 0.4.8 (MIT OR Apache-2.0) with enumflags2 0.7.12 and enumflags2_derive 0.7.12 (MIT OR Apache-2.0; the derive builds with syn 2.0.119, MIT OR Apache-2.0) and thiserror 2.0.21 (MIT OR Apache-2.0); seccompiler 0.5.0 (Apache-2.0 OR BSD-3-Clause, without its optional JSON feature); libc 0.2.191 (MIT OR Apache-2.0; constants only in our code). Both are maintained (landlock by the Landlock kernel maintainers, seccompiler by rust-vmm), neither opens a network connection, and their C-library calls are inside the crates.
- Windows only: windows-sys 0.61.2 with windows-link 0.2.1 (MIT OR Apache-2.0), through `nf-pdf-winjob`.
- Tests: nf-dxf (this workspace) for re-reading the DXF; ReportLab 5.0.1 (generator `tests/fixtures/gen_reportlab.py`, run as `python3 -I`) for three small real fixtures.

`nf-pdf2dxf` is **not in the downloadable packages yet**: `packaging/THIRD_PARTY_NOTICES.txt` is generated from the dependency graph of `nf-server`, which does not include `nf-pdf`, so it does not change; `tests/notices_check.sh` passes. Until the packages ship it, the conversion answers 503 ("the converter program ... is not installed") on a packaged installation; `deploy/install.sh` (server install from source) builds and installs it beside `nf-server`. When the program is packaged its crates must be added to the notices (the licences above are on the accepted list in `packaging/about.toml`).
- Tests only: proptest 1.12.0 (MIT OR Apache-2.0, without default features) for `tests/proptest_fuzz.rs`; flate2 as a test dependency of nf-server for compressed fixtures. Neither is in a shipped program.

## Not supported

Scanned or raster drawings (refused); encrypted files (refused); shadings and patterns (not converted); clipping (not applied); annotations (not converted); optional content (all drawn); fonts that need predefined CMaps, vertical writing, Type 3 glyph procedures, symbolic fonts without a ToUnicode map (text skipped); LZW and image filters in content (refused); colour, line width, caps, joins and fill rules (not represented); characters outside printable ASCII in text (written as `?`).

## Tests

`cargo test -p nf-pdf`: unit tests (filters, item budget, predictors against the earlier implementation, the worker's answer), geometry and container variants, refusals and every named limit (at its default value where the fixture allows, otherwise lowered), round trip through nf-dxf, command-line behaviour (`--no-text`, the 64 MiB input limit), isolation of the worker (Linux), real ReportLab files, regressions, and a fuzz run (3,000 cases in debug; `NF_PDF_FUZZ_CASES` overrides). Release fuzz: `cargo test --release -p nf-pdf --test fuzz`.

Totals at the commit of task 3.1 (`cargo test --workspace`, Linux): 307 passed, 0 failed. nf-pdf 104 (unit 18 + binary 2 + fuzz 1 + geometry 21 + isolation 5 + proptest 4 + refusals and limits 35 + regressions 2 + ReportLab 3 + command line 13); nf-server 66 unit (10 of them for this task) + 8 command line. `cargo test -p nf-server` alone needs the converter built first (`cargo build -p nf-pdf --bin nf-pdf2dxf`).
